# Load results, 2026-10-25

The three k6 scenarios of `load/`, run against the deployed gateway with the tenant gateways pointed at
the in-cluster stub (`README.md` in this folder has the method). The baseline and the concurrent
onboarding ran from `load.yml` on a GitHub-hosted runner; the noisy-neighbour pair ran from a workstation,
for the reason given in its section. Every number below is k6's own summary, measured at the client, so
it includes the network path to Sweden Central and the Gateway API proxy.

| Scenario | Objective | Result |
|---|---|---|
| Baseline | p95 under 500 ms and failures under 1 % at each rate | missed by 34 to 64 ms from 5 to 40 requests a second with no failures; saturated at 80 |
| Noisy neighbour | the protected tenant's p95, with and without enforcement | 524 ms with enforcement, 596 ms without; every protected request answered in both runs |
| Concurrent onboarding | ten tenants ready, p95 under two minutes | ten of ten ready, p95 16.3 s |

## Baseline: the gateway's ceiling

`load.yml` run 40230040873, commit `21f9da7`, k6 2.3.0 on `ubuntu-24.04`. One Business tenant with quota
enforcement off, five fixed arrival rates of 45 s each. Its gateway ran `e9905be-closeout-6`, the image it was
onboarded with on 2026-10-24: a dedicated namespace keeps the image of its onboarding (Configuration).

| Rate offered | Requests | Failed | p50 ms | p95 ms | p99 ms | max ms |
|---|---:|---:|---:|---:|---:|---:|
| 5 a second | 226 | 0 | 359 | 556 | 781 | 982 |
| 10 a second | 451 | 0 | 360 | 553 | 725 | 1,949 |
| 20 a second | 901 | 0 | 358 | 534 | 671 | 1,376 |
| 40 a second | 1,801 | 0 | 364 | 564 | 813 | 2,015 |
| 80 a second | 3,231 | 3 (0.09 %) | 3,018 | 10,059 | 13,174 | 15,644 |

- **The p95 is the path, not the load.** p50 stays between 358 and 364 ms from 5 to 40 requests a second,
  and p95 between 534 and 564 ms. Measured inside a gateway pod on the same day, the request path costs
  about 260 ms at low load, of which the embedding call on the shared Foundry account is about 200 ms; the
  rest is the runner's network path and the proxy. The 500 ms objective is missed at every rate by the
  embedding round trip, not by queueing.
- **The ceiling lies between 40 and 80 requests a second** on this cluster: at 80, p50 jumps to 3 s and
  k6 ran out of virtual users and could not start 370 of the 3,600 requests, so 80 was not sustained.
- **The added-latency objective is not verified.** `docs/operations/slo.md` sets 300 ms of p95 added by
  the gateway; this run measures the whole client path, and the in-pod figure is a low-load median, not
  a p95. The objective stands until a run measures the gateway's own time at p95.

## Noisy neighbour: isolation under a flood

Run from a workstation in Spain with k6 1.8.2 and the script of this commit; the flooding Starter gateway ran
`21f9da7` and the protected Business gateway `e9905be-closeout-6`. The Starter tenant is offered 100 requests a second for three minutes while the Business tenant asks one a
second; the second run sets `ENFORCE_QUOTA=false` on the starter gateway. The GitHub run of the same day
returned no protected-tenant series, because k6's built-in `scenario` tag overwrote the script's own tag;
the scenarios are now named `noisy` and `protected`, and `load.yml` runs the merged script.

![The protected tenant's p50, p95 and p99 with quota enforcement on and off](2026-10-25-noisy-neighbour.svg)

| Run | Protected answered | p50 ms | p95 ms | p99 ms | max ms |
|---|---:|---:|---:|---:|---:|
| Quota enforcement on | 181 of 181 | 333 | 524 | 681 | 5,129 |
| Quota enforcement off | 181 of 181 | 350 | 596 | 667 | 711 |

What happened to the flood:

| Run | Flood requests made | Answered | Rejected with 429 | Other failures | Not started by k6 |
|---|---:|---:|---:|---:|---:|
| Quota enforcement on | 15,766 | 92 | 10,975 | 4,699 | 2,234 |
| Quota enforcement off | 8,498 | 1,221 | 0 | 7,277 | 9,087 |

- **With enforcement the protected tenant's p95 was 72 ms lower**, 524 against 596 ms, and 70 % of the
  flood was stopped at the door with a 429 before any embedding call. The p99 barely moves, 681 and 667 ms.
  This is one run per condition with 181 protected requests each, so the p99 rests on two samples and the
  difference is an observation, not a proven effect: the Business tenant's own namespace and pods already
  separate it from the flood.
- **Without enforcement the flood was not even delivered.** The gateway's requests slowed until k6 hit
  its 600 virtual users and dropped 9,087 iterations, so the Starter tenant reached about 47 requests a
  second, not 100; its failures were timeouts and 5xx answers. The protected tenant's 596 ms is
  therefore the cost of less than half the flood.
- **With enforcement on, 4,699 flood requests failed with 500 instead of 429.** The gateway's Redis
  client raised `MaxConnectionsError`: redis-py 8.1 caps an asyncio pool at 100 connections by default and
  raises when a request asks for the 101st instead of waiting, and every rejected request still runs the
  quota script. The pool is per pod, so while it is exhausted every Starter tenant on that pod gets the
  500, not only the one flooding. An open defect: the pool needs a bound sized to the pod and a wait, so
  that a flood is answered with 429 and never with 500.
- **Neither run meets the 500 ms objective** for the protected tenant, for the reason the baseline gives.

## Concurrent onboarding through the admin API

`load.yml` run 40238821350, commit `21f9da7` for the script, gateway image `21f9da7-onboard-lock` on the
starter gateway, which serves `/admin`. The run reached it through the public listener, which no longer
carries `/admin`: the workflow now uses a port-forward. Ten Starter tenants ordered at once with the CI principal's
`Platform.Admin` token; each order goes to Service Bus, KEDA scales the onboarding worker from zero to
two replicas, and each virtual user polls `GET /admin/tenants/{id}` until its tenant is ready.

| Tenants | Queued (202) | Ready | p50 | p95 | max |
|---:|---:|---:|---:|---:|---:|
| 10 | 10 | 10 | 14.2 s | 16.3 s | 16.3 s |

The 61 requests k6 counts as failed are the pollers' 404s before the worker writes each tenant's
document. The earlier runs of the day failed in two ways, both fixed by this commit: a run of all three
scenarios reached the onboarding step after the OIDC assertion of its Azure login had expired, so the
workflow now logs in again before it; and, once logged in, the admin route answered all ten orders with 500,
because the Service Bus `aio` sender opens its link on the first send and is not safe for concurrent
sends, so the gateway's sends now take turns behind a lock
(`tests/test_gateway.py::test_admin_role_queues_a_burst_of_onboardings_and_tenants_cannot`).

## Configuration

- Cluster: one `Standard_D4as_v5` system node and one spot `Standard_D2as_v5` node (the regional spot
  quota of 3 vCPUs admits one), Kubernetes 1.36, Gateway API implementation `approuting-istio` with two
  proxy replicas, Sweden Central.
- Managed Redis `Balanced_B0`; Cosmos DB serverless; `text-embedding-3-small` on the shared Foundry
  account, 120 requests every ten seconds for all tenants together.
- Load tenants: `load-starter` (Starter) in `tenants-starter` and `load-business` (Business) in
  `t-load-business`, both with the PII policy `none`. Upstream: `upstream-stub` for every scenario.
- Business pods 250m / 384Mi requested and 750m / 768Mi limited; Starter pods 100m / 256Mi and
  500m / 512Mi.
- Gateway images: `21f9da7` on the starter gateway for the baseline's day and the flood,
  `21f9da7-onboard-lock` for the onboarding run, and `e9905be-closeout-6` on `t-load-business` throughout.
  `deploy.yml` updates the platform and the starter namespace only; a dedicated namespace keeps the image of
  its onboarding until the onboarding runs again.
